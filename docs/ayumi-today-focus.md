## 実コードで確認した構造

- `ayumi_projects.items` が唯一の作業データ。単発は `id/text/done`、週別は `weeks[]`、毎日は `daily.checks[]`。
- `scheduled_on` は着手予定日、`due_date` は期限。両者を流用しない。
- `overallProgress` は毎日の記録を除き、単発作業と週別チェックの完了数を集計する。既存の週別の扱いを維持した（目標の親項目数とは一致しないことがある）。休み・気づきは加算しない。
- `save` は利用者を再確認し、`user_id/id/version` 条件で更新する。応答喪失時は同一内容のみ再試行成功とする。RLSは本人かつ非匿名を対象とする。
- `app.js` の既存 `prepareChat` は未送信文章・PDF添付があると受け渡しを拒否する。既存チャットへの下書き配置だけで自動送信しない。
- AI提案APIは文字列の案を返すだけで、本人の採用後に保存する。変更していない。

## 変更ファイルと体験

- `assets/ayumi.js`：純粋な候補選択・状態変更・相談文生成、正規化と保存フィールド、既存画面の並べ替え。
- `assets/ayumi-focus-ui.js`：今日のカード、完了・休み・取り消し・選び直し、保存待ち／失敗表示、日本時間の日付変更への追従。

- `tests/ayumi-focus*.test.js`：候補・日付境界・状態遷移・相談文・DB保護。
- `scripts/preview-ayumi-focus.mjs`：本番に接続しない検証専用サーバー。テストデータはメモリ上のみ。

表示順は目標・期限・進捗 → 今日の1個 → 全体チェックリスト → 達成表示／日々の記録・気づき・管理。
候補を表示するだけでは書き込まない。同日の明示選択 → 当日予定 → 前回の未完了 → 順番の最初の未完了を優先する。
未来の着手予定、毎日・週別の項目、保管中の目標は単発候補から除く。複数の当日予定は既存の記録欄に残す。
全完了で作業は増やさず、項目ゼロでは作成へ案内する。週別だけなら全体チェックリスト、毎日だけなら日々の記録へ案内する。

「AIと一緒に進める」は選択を保存後、対象項目の相談文をチャットへ用意する。送信は本人の操作。
決定事項専用のデータはなかったため、現在の目標の最新の一言（最大500字）だけをメモとして渡す。過去の全会話から決定事項を自動抽出する機能は追加していない。

「完了して保存」は既存項目の `done` とその日の状態を同じ保存で更新する。成功前に保存済みの終了表示は出さない。
完了後はその項目に留まり、次回候補を控えめに表示する。「もう1個進める／選び直す」から本人が選べば続行可能。
休みで作業完了数は増えず、翌日は未完了から再開できる。過去の完了日を推測しない。
未保存の期限・項目・一言も一緒に保存することをカードに明示する。

## DB追加と将来の適用手順（今回は未適用）

追加は `focus_day`（nullable JSON：`date/item_id/status`）と `focus_revision` の2列。
作業のコピーは作らない。保持するのは最後に操作した日の選択と状態だけで、過去の休み一覧や連続達成履歴は新設しない。
元の毎日・週別チェックや気づき履歴は引き続き元の列で保持する。

1. テスト／ステージングDBで `20261101_ayumi_schedule.sql` までの既存マイグレーションが適用済みか確認する。
2. バックアップを確保したうえで `20261101_ayumi_focus.sql` を適用する。SQLはトランザクション、5秒ロック待ち、60秒タイムアウト。
3. 正規化・列書込権限・RLS・revision/version競合検知を確認し、その後に新しいクライアントを配信する。**未適用DBに新クライアントを配信しない**。
4. 利用者に旧タブの未保存内容を控え、再読み込みしてもらう。新クライアントで保存した目標への旧クライアント更新は、情報消失防止のため明示エラーにする。

権限追加は既存のauthenticatedロールへの新列のINSERT/UPDATEだけ。所有者RLS・匿名拒否・既存versionトリガーは変更しない。
参照項目の削除／日別変換があっても、無効になった参照を候補にしない。完了取消では `done` 状態を `active` に整える。
取り消す場合も新列を削除してデータを失わせない。旧UIへ戻すだけでは新revision付き目標を保存できないため、互換クライアントでの復旧を検討する。
